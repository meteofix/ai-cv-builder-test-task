# Architecture, the guard against invented facts, and what was simplified

Decisions with the alternatives are in [`DECISIONS.md`](DECISIONS.md); module behaviour is in [`specs/`](specs/).

## Overview

```
Browser (React SPA) ── one origin ──► web: nginx ── /api ──► api: NestJS 12 on Fastify
                                                             ├ HTTP: auth · cvs · sources · questions · pdf · /api/docs
                                                             ├ job worker in the same process (Postgres table, SKIP LOCKED)
                                                             ├ llm → Anthropic: Opus writes (author) · Opus checks (reviewer)
                                                             └ pdf → Playwright Chromium (the same HTML as the preview)
                                                             ▼
                                                         PostgreSQL 17
```

pnpm monorepo, TypeScript strict, ESM:

- `apps/api` — NestJS + MikroORM. Modules: `auth` (email/password, server-side sessions), `cvs` (CRUD, versioned saves, ownership), `sources` (PDF text extraction in a worker thread), `generation` (job engine; `compose/` holds the steps as pure functions: segments → author → review → document, questions, "Not in your CV"), `grounding` (pure: source segments, instruction lines, contacts, skill lists), `llm` (the only place that talks to Anthropic), `pdf`.
- `apps/web` — React 19 SPA (Vite, TanStack Query, react-hook-form, Tailwind 4), served by nginx, which also proxies `/api`.
- `packages/shared` — zod schemas: the one CV document schema, request/response contracts, the route table, error codes and limits. The API validates with them, the web client parses responses with them, Swagger is generated from them (`/api/docs`).
- `packages/cv-template` — the CV as React markup and CSS. The preview and the PDF render the same HTML.

## Main decisions

- **Generation is a background job**, never inside an HTTP request. `POST /api/cvs` answers 202 at once; the job lives in a Postgres table claimed with `FOR UPDATE SKIP LOCKED`, under a 30 s lease with a heartbeat and fencing (every write of the worker checks it still holds the job). Each step's result is stored: a restarted API resumes at the first unfinished step and skips the steps whose result was committed. A call interrupted before its result was stored can be repeated, and an incompatible stored result is regenerated. No Redis and no separate worker: one process is enough at this scale, and the queue is transactional with the data.
- **Progress by polling** `GET /api/cvs/:id/job` every 1.5 s while a job is active, as steps (Writing · Checking the text · Finishing). There is no draft on the way: the author writes the whole CV in one call.
- **One JSON document per CV with a `version`.** A save from a stale tab gets 409; its form is then replaced by the latest saved version and says so. Autosave is single-flight, and typing during a successful save is not lost. The editor is read-only while an AI job changes the CV.
- **Server-side sessions** in Postgres (httpOnly `SameSite=Lax` cookie, argon2id), so logout really revokes. CSRF protection by Fetch Metadata, security headers and rate limits on sign-up and login.
- **Ownership in the data layer.** Every CV route goes through `findOwned(id, userId)`; a foreign id is a 404. Worker reads are scoped to the job's owner. A table-driven test runs every CV route as a second user.
- **Errors** are RFC 9457 `problem+json` with a stable `code` and a `requestId` (proxy errors from nginx are not); the web app maps codes to messages. Logs are JSON (pino) with request and job ids, token counts and latency of every LLM call. Our own log fields carry no CV content; an unexpected exception's message and stack are logged unscrubbed.

## How the AI is kept from inventing facts

Principle: **code guards what is mechanically checkable, a model reviews meaning, and what is left becomes a visible question.** Code never decides whether a sentence is true. The reviewer's work is measured by the [evals](evals.md), not proven by the tests.

1. **Segments (code).** The source (PDF text read by layout, or pasted text) becomes numbered segments `S1…Sn`: one per line, a long line split into sentences. A segment that matches one of nine instruction patterns (mostly English; invisible characters are removed before matching, every line of a multi-line answer is checked) is cut before any model sees it and listed as "Ignored as an instruction". This is the first layer only. Everything else reaches the models inside `<cv_source>`, declared as data; every answer must pass a schema; the reviewer reads the result; the contacts are checked in code.
2. **Author (Claude Opus).** Writes the whole CV for the target role in the source's structure, citing the source segments behind each item. An item either **keeps** segments (the server copies their text, normalising list markers, whitespace, soft hyphens and the final full stop) or is **rewritten** and cites its evidence. The author also reports what it left out and why, what is missing or vague, and why an older job comes first when it does. The answer is validated by a zod schema and by checks that need the source (every id is a real segment, dates `YYYY` or `YYYY-MM`, limits after kept text is filled in); a failure is asked again once, never cut.
3. **Contacts (code).** Email, phone and links the author proposes are kept only when they appear in the source (case, whitespace and line wraps normalised). A handle is not a link, except a handle the source labels as Telegram, which becomes its `https://t.me/` link; other handles go to "Not in your CV". Names and locations are not matched by code; the reviewer sees them.
4. **Reviewer (Claude Opus, its own prompt).** Sees the whole CV with each item's segments next to the source and returns only problems, each a `fix` (corrected text with its segments) or an `ask` (the item is taken out and becomes a question). It judges support only, not relevance, order or style, and names a class: an invented detail, an inflated scope, a changed scope, a wrong time, a wrong job, a wrong number. It also sees the segments the author called headings and may return one that holds content.
5. **Accounting (code + reviewer).** Every content line of the source is either cited by an item of the CV or shown in "Not in your CV" with a reason and, where the CV has room, an "Add" button (an ignored instruction has none). That is a citation-level contract. Whether a rewritten item keeps every fact of the line it cites is judged by the reviewer, measured by the evals, and not guaranteed by code. A line a record header cites (a GPA, honours, a company description) counts as placed only if the header shows it: what it does not show is listed in "Not in your CV" (decision 040). After an answer, every earlier AI item the rewritten part no longer shows word for word goes to "Not in your CV" as earlier wording.
6. **Questions and answers.** What is missing, vague or taken out by the reviewer becomes a question, up to 10 per generation; findings past the cap are listed in "Not in your CV", but the author's gaps and missing-date questions past it are dropped. A dates answer, and a direct-field answer (company, title; cut to 200 characters), are applied without a model. A text answer becomes a segment `A<n>`: the author rewrites only the part the question is about, the reviewer checks the new items, and nothing else in the CV changes.

All model output goes through zod schemas. A run makes at most 15 model calls by default (`LLM_CALL_BUDGET`; every HTTP attempt and re-ask counts), and a manual Retry starts a new run. The tests use a scripted model and prove the mechanics: kept text is copied, an invented contact is dropped, an instruction line never reaches a model, a reviewer's `ask` takes the item out, an answer changes only its part, an over-limit answer is asked again.

**Experience order and relevance.** The experience is newest first; the author may put an older job first only when it is clearly more relevant, and then gives a reason the editor shows. Less relevant content is shortened, but the bar is deliberately high ("when unsure, keep it"), so for an adjacent role the CV is mostly reordered and retargeted rather than cut; a different profession is cut down to the bullets that carry over. This is a prompt policy, measured by the evals and not guaranteed by code (decision 035, revising 033).

## What was simplified, and what would come next

| Simplification                                                                                                                                                                           | Why                                                                      | Next                                                                                                                           |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| Job queue in Postgres, worker in the API process                                                                                                                                         | No new infrastructure; transactional with the data                       | A separate worker process (same table), or a queue service                                                                     |
| Polling, no sections on screen while the author writes                                                                                                                                   | Simple and survives reloads                                              | Stream the CV's sections as the author writes them (perceived speed)                                                           |
| Text-layer PDFs only, no OCR                                                                                                                                                             | OCR is a project of its own                                              | OCR; for now a clear "paste the text" message                                                                                  |
| PDF layout: up to two columns, a header band, a narrow date column, short tables                                                                                                         | Covers the common layouts, measured on a corpus                          | Long tables, three columns, rotated text                                                                                       |
| Questions are created once per generation; an answer rewrites one group                                                                                                                  | Predictable and cheap; nothing else moves                                | A conversational mode; an answer that restructures a job                                                                       |
| One template; a version column and a reload on conflict                                                                                                                                  | Several templates are out of scope; devices cannot overwrite each other  | More templates; field-level merge                                                                                              |
| A daily limit that counts starts: a generation, a text answer, a retry                                                                                                                   | Protects the API budget; a start is not the spend of its calls           | Cost accounting from the stored token counts, per-plan limits                                                                  |
| Faithfulness rests on the reviewer, measured, not proven                                                                                                                                 | Code rules lost content on real CVs (decision 035)                       | More planted kinds in the reviewer test; hints on numbers and names                                                            |
| Length is a prompt rule; the page count is advice in the editor                                                                                                                          | A "measure pages → shorten" loop costs a call and cuts text              | The loop, if CVs still go past two pages                                                                                       |
| A company description has no field; it goes to "Not in your CV"                                                                                                                          | A new field changes the schema, the template and both prompts            | A field under the company that the author writes and the reviewer checks                                                       |
| Silent cuts: a long direct answer, questions past 10, provenance ids past 60                                                                                                             | Bounded sizes; a rewrite of the contracts is out of this slice           | Refuse or note each cut; keep the dropped questions in the panel                                                               |
| Web: a stalled request has no timeout; polling gives up silently after repeated errors; a finished job can replace unsaved edits                                                         | Small, found by the final audit                                          | Request timeouts, a visible give-up state, a retry control for autosave                                                        |
| Retry and answer routes have no extra throttle; a wedged Chromium is not recycled                                                                                                        | Local deliverable behind a login                                         | Throttle the routes, bound the worker and render queues, recycle the browser                                                   |
| `factIds` and the `facts` column keep their pre-v2 names; the `extract` step id and the `judge` names remain                                                                             | A rename is a contract and migration change                              | Rename to segment ids and `analysis`; drop `extract`                                                                           |
| The `llm` module depends on `generation` and writes the job table; some controllers use the `EntityManager` directly; `GET /draft` always returns null; Swagger at `/api/docs` is public | Found by the architecture audit; each is a refactor or a contract change | An `LlmBudget` port owned by `llm`; services behind the controllers; drop the draft route; gate Swagger by an environment flag |
| Unexpected exceptions are logged with their message and stack, unscrubbed; a driver message can embed a value                                                                            | Local deliverable; the fields are named in the filter                    | Log only the error class, code, constraint and routine for driver errors                                                       |
| `eval/` ships in the API bundle; `pdf-layout.ts` is 366 lines                                                                                                                            | Not reachable at runtime; a split is a refactor                          | A separate eval build; split column detection from line assembly                                                               |
| Completeness of a rewritten item is checked by the reviewer, not by code                                                                                                                 | A mechanical check gave false flags                                      | An enforced completeness check                                                                                                 |
| "Not in your CV": "Add" does not show where the item went; a vague source line stays after its question is answered; a job detail ("Full-time") added back becomes a bullet              | Cut for time (UI/UX)                                                     | Scroll to and highlight the added item; hide answered lines; a field for job details                                           |
| An answer changes only the part its question is about: new experience in an answer ("2 years as a barista") updates the summary but does not create a position                           | Predictable; nothing else in the CV moves                                | An answer that adds a record and asks for its dates                                                                            |
| The ↑/↓ arrows move one position; a foreign position placed between positions of one company splits the company block                                                                    | Positions are separate records                                           | Move a company block as a whole                                                                                                |
| The preview is one continuous page; page breaks exist only in the PDF                                                                                                                    | `paginate()` runs right before printing                                  | A4 sheets in the preview, split by the same `paginate()`                                                                       |
| No error tracker; CI builds images from scratch; Chromium sandbox off in its own container                                                                                               | Structured logs are enough locally; simpler workflow                     | Sentry; layer cache; a rendering service                                                                                       |
