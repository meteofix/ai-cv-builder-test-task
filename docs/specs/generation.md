# Generation — job engine, LLM client, pipeline, draft, answers

**Area:** `apps/api/src/generation/`, `apps/api/src/llm/`, tests `apps/api/test/generation.*`, `apps/api/test/llm.*` and helpers in `apps/api/test/generation/` (the fake LLM client). **Builds on (main, frozen at S0):** `GenerationQueue` and `toJobDto` (`common/generation-queue.ts`), `findOwned`, `ApiError`, the entities (`generation_jobs`, `cv_sources`, `cvs`, `cv_questions`), `ROUTES.getJob|retryJob|getDraft|getNotInCv` and the DTOs in `@cv/shared`; [grounding.md](grounding.md) for segments, instruction-like text and contacts. Decisions: [002](../DECISIONS.md#002-background-worker-inside-the-api-process), [003](../DECISIONS.md#003-job-queue-in-a-postgres-table), [006](../DECISIONS.md#006-two-step-generation-from-verified-facts)–[010](../DECISIONS.md#010-structured-output-and-a-per-job-llm-call-budget), [013](../DECISIONS.md#013-staged-draft-assembled-on-read)–[015](../DECISIONS.md#015-the-cv-keeps-the-source-language), [023](../DECISIONS.md#023-template-questions-and-targeted-answers), [035](../DECISIONS.md#035-v2-an-author-and-a-reviewer-instead-of-verified-facts), [036](../DECISIONS.md#036-what-v2-leaves-out-on-purpose).

## Goal

Turn the source text — a CV or the person's own account of their experience — into a CV for the target role, in the background, surviving page reloads and API restarts, with visible steps, a clear failure instead of an endless spinner, and questions for what is missing, vague or unsupported. The model does the work about content: it reads the source, decides what to show and how, writes, checks and corrects. The code keeps the contracts, the safety boundary, exact contacts, the accounting of what did not reach the CV and the safeguard limits; it passes no verdict on content (decision 035). Nothing of the source disappears silently: it is in the CV, or in "Not in your CV" with a reason. An answer updates only its part of the CV.

## Contracts

| Route (`ROUTES.*`)                        | Success                                                     | Errors (besides 401, 404 `CV_NOT_FOUND`)                              |
| ----------------------------------------- | ----------------------------------------------------------- | --------------------------------------------------------------------- |
| `getJob` `GET /api/cvs/:id/job`           | 200 `Job`                                                   | 404 `NOT_FOUND` when the CV has no job (not reachable via the API)    |
| `retryJob` `POST /api/cvs/:id/job/retry`  | 202 `Job`                                                   | 409 `JOB_ACTIVE`, `JOB_NOT_RETRYABLE`; 429 `GENERATION_LIMIT_REACHED` |
| `getDraft` `GET /api/cvs/:id/draft`       | 200 `{draft: null}` (no draft in v2)                        | —                                                                     |
| `getNotInCv` `GET /api/cvs/:id/not-in-cv` | 200 `{items: NotInCvItem[], sourceCoverage?, orderReason?}` | —                                                                     |

Every handler calls `findOwned` first. `getJob` and `retryJob` use `GenerationQueue.getLatestJob` and `GenerationQueue.retry`; the `Job` shape comes only from `toJobDto`.

**`LlmClient`** (`llm/llm-client.ts`) owns every retry, the call budget and the re-asks; one HTTP attempt goes through the port **`LlmTransport`** (`llm/llm-transport.ts`), whose only implementation is `AnthropicTransport`, the only file that imports `@anthropic-ai/sdk`:

```ts
class LlmClient {
  parse<T>(request: {
    role: 'author' | 'reviewer' | 'extractor' | 'writer' | 'judge'; // the last three: apply_answer until V2-Z3
    system: string;
    cached?: string; // sent first in the user turn, marked for prompt caching (the source)
    input: string; // the rest of the user turn; source text only inside <cv_source>…</cv_source>
    schema: z.ZodType<T>; // what the service is asked to follow
    check?: (output: T) => string | null; // what the schema cannot say; a problem is re-asked
    job: { id: string; lockedBy: string }; // for the call budget and fencing
    signal: AbortSignal; // lost lease or shutdown
  }): Promise<T>;
}

abstract class LlmTransport {
  abstract send<T>(request: TransportRequest<T>, signal: AbortSignal): Promise<TransportResult<T>>;
  // TransportResult: { kind: 'output', output } | { kind: 'invalid', error } | { kind: 'refusal' };
  // a failed request throws TransportError('transient' | 'auth' | 'rejected', status, retryAfterMs)
}
```

Errors `parse` throws carry a job error code (`JobError`): `AI_UNAVAILABLE` (transient, the job may retry), `AI_LIMIT_REACHED`, `AI_REFUSED`, `AI_KEY_REJECTED`, `INTERNAL` (invalid output after the re-ask, or any other rejected request); a charge that finds the job no longer held by this worker throws `LeaseLostError`. Tests replace the transport, not the client, with a scripted `FakeLlmClient` through `createTestApp(..., { overrides: [{ provide: LlmTransport, useValue: fake }] })`, so retries, the call budget and re-asks always run the real code; `llm.acceptance.spec.ts` runs the production SDK client (`createAnthropicSdk`: `maxRetries: 0`, the configured timeout) against a local HTTP server it reaches through `ANTHROPIC_BASE_URL`. Waits between attempts go through `LLM_SLEEP`, which tests replace. The real API is never called in tests except under `RUN_LIVE=1`.

## Behaviour

### 1. Job engine

1. **Worker loop** (when `WORKER_ENABLED=true`): a unique worker id per process; it calls `processNext()` and, when there was nothing to do, waits 1 s. An error in an iteration (for example the database is down) is logged and the loop waits 1 s, 5 s, then 30 s between further failures; it never stops by itself. Tests run with `WORKER_ENABLED=false` and call `processNext()` directly; time comes from an injectable clock.
2. **`processNext()`** claims one job in a single statement — `queued` with `run_after <= now`, or `running` with `locked_until < now` (a dead worker's lease), ordered by `run_after`, `created_at`, `FOR UPDATE SKIP LOCKED` — sets `status = 'running'`, `locked_by`, `locked_until = now + 30 s`, `attempts = attempts + 1`, and runs it until it succeeds, fails, is re-queued or is released. It returns whether it processed a job. A claimed job whose `attempts` would exceed `max_attempts` (its workers kept dying) is marked `failed` with its last error instead of running; the last error is the one stored when it was last re-queued, else `INTERNAL`.
3. **Heartbeat** every 10 s extends `locked_until` where `locked_by` is this worker. When the update matches no row (lease lost, CV deleted), the job's `AbortSignal` fires and the worker stops the job without further writes. A heartbeat that cannot reach the database is logged and the lease is left to run out.
4. **Fencing.** Every write of the worker (step result, `llm_calls`, finalization, failure) has `WHERE id = :id AND locked_by = :worker`; a write that matches no row aborts the job silently (logged at info). A fenced transaction that also writes other rows of the CV (facts, document, questions) locks the CV row first (`SELECT … FOR UPDATE`), in the order a CV delete takes its locks — the CV row, then its jobs, then its sources and questions (the cascade triggers fire in the order the migration created the foreign keys: `generation_jobs`, `cv_sources`, `cv_questions`) — so a delete during finalization waits instead of deadlocking. A failure writes only the job row (and, for `apply_answer`, its question under the same CV lock). `GenerationQueue.retry` locks the job and then, for `apply_answer`, the question without the CV lock; it stays clear of a delete only because the delete reaches the jobs before the questions.
5. **Steps** — `generate`: `write → judge → finalize` (the author, the reviewer, the assembly; `extract` stays in the step enum for jobs stored before v2 and is never entered); `apply_answer`: only the steps its answer needs. `step` is the step that runs now or runs next: right after the claim the engine sets `step` to the first step of the kind when it is null (`write` for `generate`, the first step its answer needs for `apply_answer`), and a step's result is written to `generation_jobs.state` together with the name of the next step in one fenced update. A resumed job starts at `step`: a restart never repeats a finished LLM call. The web app shows the steps as Writing → Checking facts → Finishing.
6. **Failures.** `AI_UNAVAILABLE` → if `attempts < max_attempts` (3): back to `queued`, `run_after = now + 10 s / 30 s / 60 s` (by attempt), lease cleared, the code and message kept on the row (the API shows them only once the job has failed); otherwise `failed`. Every other code → `failed` at once. An unexpected exception (a bug, a database error) is logged without driver row values (name, message, code, stack — as the global error filter does) and handled like `AI_UNAVAILABLE` with the code `INTERNAL`; so is a handler that returns without finishing the job. A failed job keeps `step` (where it stopped), `error_code` and a user-facing `error_message` without CV content; for `apply_answer` the question gets `applyStatus = 'failed'`.
7. **Shutdown.** On application shutdown (`beforeApplicationShutdown`, before the database closes) the loop stops claiming, the in-flight job is aborted and released: `status = 'queued'`, lease cleared, `attempts` decremented (a shutdown is not a failed attempt). Shutdown then waits up to 5 s for the aborted job to unwind.
8. **Deleted CV.** The cascade deletes the job; the next fenced write matches nothing and the worker drops the job.

### 2. LLM client

1. Models and effort by role, from the environment with defaults: author `AUTHOR_MODEL` (`claude-opus-5-5`), `AUTHOR_EFFORT` (`medium`); reviewer `REVIEWER_MODEL` (`claude-opus-5-5`), `REVIEWER_EFFORT` (`medium`); the roles of `apply_answer` until V2-Z3 as before (extractor `EXTRACTOR_MODEL`/`low`, writer `WRITER_MODEL`/`medium`, judge `JUDGE_MODEL`/`high`). Two output modes (`LlmRequest.output`, decision 036): `grammar` (the default, the reviewer) — `client.messages.parse({ model, max_tokens, system, messages, output_config: { effort, format: zodOutputFormat(schema) } })`; `tool` (the author) — `client.messages.create` with one tool `answer` whose `input_schema` is the zod schema as plain JSON Schema (not `strict`), `tool_choice: {type: 'auto', disable_parallel_tool_use: true}` (Opus 5.5 refuses a forced choice) and a line in the system prompt asking for one call of it; the tool input goes through the zod schema, and an answer without the call, with another tool, or with an input the schema refuses is invalid output (5.) and asked again. Both with `max_tokens` 32 000 for the author and 16 000 for the other roles; no `temperature`; SDK `maxRetries: 0`, `timeout: LLM_TIMEOUT_MS` (300 s); the job's `AbortSignal` is passed through. A request with `cached` sends the user turn as two text blocks, the first (the source) with `cache_control: ephemeral`, so a re-ask reads the source from the cache.
2. **Call budget.** Before every HTTP attempt the client increments `llm_calls` with a fenced `UPDATE … SET llm_calls = llm_calls + 1 WHERE … AND llm_calls < LLM_CALL_BUDGET` (15); no row → `AI_LIMIT_REACHED` (or `LeaseLostError` when the job is no longer held by this worker), no request is sent. A charge happens also for every transport retry and every re-ask.
3. **Transient errors** (429, 500, 502, 503, 504, 529, connection errors, timeouts): up to 3 attempts per call, waiting `retry-after` (seconds or HTTP date, at most 30 s; zero or a past date counts as absent) or 1 s, then 2 s; then `AI_UNAVAILABLE`.
4. **No retry:** 401/403 → `AI_KEY_REJECTED`; any other status → `INTERNAL`; `stop_reason: 'refusal'` → `AI_REFUSED`, also when the refusal carries text (the stop reason is checked before the schema error, which the transport keeps instead of throwing).
5. **Invalid output** (no parsed output, a schema error, `stop_reason: 'max_tokens'`, a U+0000 character or a lone surrogate in any string of the answer, which Postgres cannot store in `jsonb` — the six characters `\u0000` typed as text are fine — or a problem the request's `check` reports): the request is sent once more with the original input and the problem appended inside `<previous_answer_error>`; a second invalid answer is `INTERNAL` ("The AI returned an answer we could not use"). The checks stay out of the schema sent to the service because a refined schema compiles to a grammar the service refuses as too large. The output is never `JSON.parse`d by hand.
6. **Logging**, one line per HTTP attempt (`llm call`): job id, role, model, input/output tokens, cache read and write tokens, `latencyMs`, `stopReason`, outcome (`output`, `invalid`, `refusal`, `transient`, `auth`, `rejected`) and the HTTP status of a failed request. Never the prompt, the source, the answer or a check's message (it can quote the CV).

### 3. `generate`

The steps are pure functions in `generation/compose/` (`prepareSource`, `authorRequest`, `reviewRequest`, `compose`); the handler runs one per job step, the eval runs them in a row.

1. **Segments** (grounding.md §2). The source becomes numbered segments `S1…Sn`; instruction-like segments are cut before any model sees them: they are not in `<cv_source>`, they cannot be cited, and they show as `ignored` in "Not in your CV". Both models get the same source block, `<cv_source>` with one `Sk: text` line per segment, declared to be data; a `<cv_source`, `<target_role>` or `<cv_document` tag in user text gets a space before its name so it cannot close a delimiter.
2. **write — the author.** Input: the source block (cached) and `<target_role>`. Output (`authorOutputSchema`): `locale`; `contacts` `{field, value, segment}`; `headline`, `summary[]` and the items of every group as items `{text, segments}`, where `text: ""` keeps the cited segments word for word and a text is a rewritten or new item whose segments are its evidence (anywhere in the source); jobs `{title, company, location, start, end, current, segments, groups}`, a group being `{title ("" for a plain list), items}` (decision 036), in the order the author chooses (newest first unless `orderReason` says why an older job leads); education `{institution, degree, start, end, segments}`; `additional` sections `{title, entries}`, an entry `{title, start, end, segments, groups}` (a project, a course with its provider, a certificate; a title alone is an entry); skill groups `{title, segments, items}`, where empty `items` means the server cuts the cited lines into skills; `notIncluded` `{segments, section, job, reason}`; `headings` (segments that are only headings, labels or decoration); `gaps` `{kind: missing_dates | missing_company | missing_title | missing_institution | vague, job, education, question}` most important first (`job` and `education` here and in `notIncluded` are 1-based, 0 for none, and an omitted one is read as 0); `orderReason` (one short sentence for the person on why an older job comes first; "" for newest first); `structureNotes` (see below). Empty strings and 0 stand for "none" (a date "" is converted to null in one place, `dateOf`), and the answer comes as the input of a tool call the service does not constrain (`output: 'tool'`, §2): with groups and entries the schema no longer fits the service's grammar cap (decision 036). Date fields describe their format (`YYYY` or `YYYY-MM`) in the schema. The prompt also carries the grouping rules (keep the source's subsections by default, merge layout artifacts and one-item groups, note a merged or dropped subsection and why in `structureNotes` — stored with the answer and printed by the eval, never shown to the person and never logged (it can quote the CV); content of a dropped subsection that is not in the CV goes into `notIncluded` with its reason; without subsections in the source, group a job's bullets only when the list is long, about 8+, with clear themes, and skills from about 12), the compression rule (one source item → one bullet of one or two lines; split a paragraph only for several different achievements; keep only what is already concise) and the summary rules (about 400–600 characters for the target role: years, field and kind of companies first, then one or two sentences of strengths and results; one grammatical person; no list lines; paragraphs separated by a line break). The prompt states the principles and the rules the code relies on, with one invented example; quality is measured by the evals. The answer must also pass `check` (§2.5): every cited id is a segment the model saw; a kept or rewritten item cites at least one segment; dates are `YYYY` or `YYYY-MM` or ""; every plain string (titles, names, reasons, questions) fits 200 characters; at most 10 groups in a list; `job` and `education` numbers name an entry; and, with kept text filled in, the document fits `LIMITS` — at most 30 jobs, 20 bullets per job (the plan said 15; a real CV in the dev corpus has 17 shared by one company, so 20, pending the owner — question V2-Q1), 400 characters per bullet, a summary of 1000, 120 skills, 20 extra sections of 40 entries, 20 bullets across the groups of a job, 20 lines across the groups of an extra entry; an extra entry has a title or a line, and a skill group names a skill (the document would drop either, and the segments it cites would count as placed while shown nowhere). A limit is a safeguard real CVs do not reach: an answer over it is asked again, never cut. The answer is stored in `state.write`.
3. **The draft** (`buildDraft`, code). Kept items get the text of their segments: lines of one item joined with a space, a leading list marker (`•`, `·`, `▪`, `●`, `◦`, `‣`, `∙`, `*`, `-`, `–`, `—`, `1.`, `1)`) and soft hyphens removed, runs of spaces collapsed. Contacts (grounding.md §4): an email, phone or link the source does not contain is dropped (the editor shows the empty field); a link gets `https://` when it has no scheme; at most 5 links, duplicates once. The name and the location are kept as the author gives them; the reviewer checks them. A headline without evidence becomes the target role.
4. **judge — the reviewer.** Input: the source block (cached), `<target_role>`, and `<cv_document>`: every item of the draft with its id — `name`, `location`, `headline`, `summary.N`, `job.N.title|company|location|dates`, `job.N.M` (bullets, numbered across the job's groups), `job.N.gK` (the title of a titled group), `edu.N.institution|degree|dates`, `skills.N` (the skills of a group), `skills.N.title` (its title, when it has one), `extra.S.E.title|dates`, `extra.S.E.M` (lines of an entry), `extra.S.E.gK` — each item marked `unchanged` (kept) or `rewritten` with its segments. Output (`reviewOutputSchema`): only problems, `{item, action: fix | ask, class, text, segments, question}`; items it does not name are fine. The prompt prefers `fix` (the smallest truthful version, with its evidence) and keeps `ask` for an item nothing in the source supports; it checks unchanged items only for where they stand, and forbids judging relevance, selection, order, style or length. Classes (`invented_detail`, `inflated_scope`, `wrong_time`, `wrong_job`, `wrong_number`, `other`) are for logs and evals only. `check`: every item id exists, every segment id exists, a fix has text and fits its item's limit, a fix of a text item other than the headline cites evidence (a group title needs none: it names the items under it), and a fixed date reads as `YYYY[-MM] – YYYY[-MM]` or `present`. A reviewer that fails (twice invalid, refused, unavailable) fails the job like any step: unchecked text never reaches the CV. The answer is stored in `state.judge`.
5. **finalize** (`compose`, code). From the stored answers: the draft; the review applied (the first finding per item counts) — a fix replaces the item's text and evidence, or sets the field (a fixed date sets start, end and current); an ask takes a text item out of the CV and makes it a question, empties a field (of a job, a school or an entry) and asks for it, drops a doubtful group title without a question (its items stay as a plain list; a fixed title loses a trailing colon, which the template adds to a skill group), and turns a doubtful headline into the target role without a question; then the document (`toDocument`: ids `p1…` for jobs, `p1-g1…` for their groups, `p1-b1…` for bullets (numbered across the groups, so a bullet keeps its id when it moves to another group), `e1…`, `k1-1…`, `a1…`, `a1-e1…` for entries, `a1-e1-g1…` and `a1-e1-i1…` for their groups and lines; a group with no item left is left out, an entry with neither a title nor a group is left out; `factIds` are segment ids; `factId` of a job or school is its first segment; skill groups stay groups (`k1…` with skills `k1-1…`, the title or null), in the author's order, a group with no skill left out; an extra section with no entry left is left out; the bullets of all jobs get one ending style, the one most of them have — a final full stop, or none on a tie — and only that stop changes, never past `LIMITS.maxBulletChars`; a bullet ending in other punctuation stays as it is), validated with `cvDocumentSchema`; the questions (§3.6); "Not in your CV" (§4) stored in `cv_sources.facts` as `{version: 2, locale, notInCv, coverage, orderReason}`. One transaction, read the CV fresh, write the document with `version = version + 1` and `updated_at = now()` (compare-and-set; a conflict is a retryable `INTERNAL`), insert the questions with strictly increasing `createdAt` in their order, mark the job `succeeded`; all fenced.
6. **Questions**, at most 10, in this order: the reviewer's asks (each its own question: `unverified` with the reviewer's question and, as `context`, its proposed text or the item; for a field `missing` with the field, `dates` as `answerType` for dates); then the author's gaps in its order (`vague` with the author's question, target its job or the summary; `missing_*` only when the field is still empty after the review, with the author's question or a template); then a safety net: a job whose dates are incomplete (no start, or no end while not current) or whose company is empty, that nobody asked about, gets the template question (the task requires asking for missing information). A field is asked about once. A reviewer's ask past the cap is not lost: what it took out is listed in "Not in your CV" (§4) with the reviewer's question as the reason.

### 4. Draft and "Not in your CV"

1. `GET /draft` answers `{draft: null}`: there is no draft before the author has written the CV; the screen shows the steps.
2. `GET /not-in-cv`: `{items: []}` before the first v2 generation ends (also for a CV generated before v2); otherwise the stored items and `sourceCoverage`. Items, in this order: `not_included` — the author's `notIncluded` entries whose segments the CV does not cite (the text of those segments, `context` = the author's reason, `section`, and for a job the `itemId` of that job), then what reviewer asks past the question cap took out (`context` = the question); `not_placed` — every content segment (one with a letter or a digit, not instruction-like) that nothing cites: not the final draft (items taken out for a question included, since the question shows them), not `notIncluded`, not `headings`, word for word; a segment the author calls a heading counts only when it is at most 60 characters without its spaces (a heading may be letter-spaced), so content cannot hide there; `ignored` — the instruction-like segments. `sourceCoverage`: `contentLines` = content segments, `notRecognized` = `not_placed` items, `low` when that is more than a quarter. `orderReason`: the author's reason for putting an older job first, only when it gave one; the editor shows it above the experience.

### 5. `apply_answer`

Until V2-Z3 a content answer runs the earlier flow below on facts stored before v2; a CV generated by v2 has none, so its content answers fail (`INTERNAL`). Dates and named fields read no facts and work for every CV.

The job's `payload` is `{questionId, answer}` (`applyAnswerPayloadSchema`), its `target` is the question's target. The finalization of every case reads the document fresh and writes it with `version + 1` (and `updated_at = now()`) in one fenced transaction together with the question's `applyStatus` and `applyNote`; no new questions are created. When the target item no longer exists (the user deleted it with a manual save), nothing in the document changes, the job `succeeds`, and the question gets `applyStatus = 'failed'` with `applyNote` "The part of the CV this answer was for no longer exists." In code: the field of the target is read from the question row (the job's `target` has no field). A `dates` answer starts at `finalize`; a `text` answer starts at `write`, and a text answer to a named field is applied at once without the LLM. A content answer whose target is not a position of the document or the summary is handled like a target that no longer exists. A named-field answer aimed at the wrong kind of item (a company for an education entry) changes nothing and gets `applyStatus = 'failed'` with "This answer does not fit the part of the CV it was asked about."; a job whose question row is missing fails with `INTERNAL`.

1. **Dates** (`answer.type = 'dates'`): set `start`, `end`, `current` of the target position (`start`, `end` for education and for an extra entry, whose `itemId` is the entry's id, `a1-e1`; `current` leaves its end empty); no LLM call; `applyStatus = 'applied'`. The stored facts keep the dates and the judged `current` from generation: a dates answer changes only the document, so the judge's position labels and a later answer's writer still see the generated dates.
2. **A field** (`text` answer, target with `field` in `company`, `title`, `location`, `institution`, `degree`; `title` of an extra entry): set the field to the trimmed answer (at most `LIMITS.maxFieldChars`); no LLM call; `applied`. A dates or field answer aimed at a whole extra section, or a field the target does not have, is `failed` with the mismatch note. An extra entry whose title or dates the review asked about stays in the document even when it is left empty, so its answer has a place to go (unless that question fell past the cap of 10). Known limit: the editor drops an entry with no title, no dates and no line from every save, so an edit before the answer removes such an entry and its answer is then `failed` as gone.
3. **Content** (`text` answer to a position without a field, or to a removed/vague item): the answer becomes an achievement fact of that position (its quote is the answer, verified against the answer text). The writer regenerates only the AI-written bullets of that position (bullets with non-empty `factIds`) from the position's facts plus the answer; references and numbers are checked against the source and the answer; the judge checks the new bullets. The position's bullets become the passing new bullets followed by the user-written bullets (`factIds: []`) in their original order, cut to `LIMITS.maxBulletsPerPosition`. Other positions and sections are not touched. A target in `summary` regenerates only the summary the same way. All new items passed → `applied`; some were removed → `partial` with `applyNote` "Some of the new text could not be verified and was left out." In code: the answer fact has the id `answer-<job id>` and is stored in `cv_sources.facts.answers` when the answer is applied, so a later answer to the same position builds on it; its span points into the source with every stored answer appended on its own line, and that text is what references and numbers are checked against. The writer gets only the target position's facts (the position, its achievements and earlier answers to it) plus the new one; for the summary, every fact. Regenerated items get new ids; a regenerated summary is the passing sentences only. Verified content is never replaced by nothing: when none of the new text passes (or the writer returns none), the position's bullets or the summary stay as they were and the question is `partial` with "None of the new text could be verified, so this part of your CV was left as it was."; the answer fact is stored either way. User-written bullets are never cut: the regenerated ones fill only the room the limit leaves (`partial` when some did not fit). A summary the user wrote (non-empty text, no `factIds`) stays as it is, `partial` with "You wrote the summary yourself, so it was left as it was.".

## Acceptance examples

Test file `apps/api/test/generation.acceptance.spec.ts` (and `llm.acceptance.spec.ts` for the client against a fake HTTP server). Each test name starts with the example id. Data comes from the factories; the LLM is a scripted `FakeLlmClient` that records the requests it receives; the worker is driven with `processNext()`.
